# BlockForge Universal API (v1)

One provider-neutral HTTP API for AI systems that can call tools/functions or send HTTP requests. Provider adapters belong in the client; the API contract stays the same.

## Architecture

AI provider -> BlockForge API -> BlockForge core + GitHub repository

The AI decides what the user wants and proposes files. BlockForge validates inputs, checks JSON, writes a new project branch, and opens a pull request. It never pushes AI-generated project files directly to the default branch.

## Current v1 tools

- list_repo_files: list repository paths from the configured default branch.
- read_repo_file: read a UTF-8 text file from the repository.
- validate_json: parse and validate JSON text.
- create_addon_project: create a branch under projects/<slug>/, commit the supplied files, and open a pull request.

The API does not claim that a project is a working add-on merely because its JSON parses. Bedrock schema/version validation and .mcaddon packaging are later engine milestones.

## Run locally

Requires Node.js 20 or newer. No npm dependencies are required.

1. Copy .env.example values into your server environment.
2. Set BLOCKFORGE_API_KEY to a long random secret.
3. Set GITHUB_TOKEN to a fine-grained token or GitHub App installation token with Contents: read/write and Pull requests: read/write on this repository.
4. Set GITHUB_REPOSITORY=prohexa65-spec/BlockForge-AI.
5. Run npm run api.

Never put either secret in browser JavaScript, a public AI prompt, a GitHub Pages site, or a repository file. Use a server secret store. A GitHub App is preferred for a production deployment.

## Authentication

Every endpoint except GET /v1/health requires Authorization: Bearer <BLOCKFORGE_API_KEY>. Use HTTPS in deployment. Configure ALLOWED_ORIGIN to the exact frontend origin; do not leave it as * for a public production service.

## HTTP contract

- GET /v1/health
- GET /v1/tools
- POST /v1/tools/call with { "name": "...", "arguments": { ... } }

See openapi.yaml and examples/tool-definitions.json for the API and provider-neutral tool schemas.

## Provider integration

Each AI provider should translate its native tool/function format to the shared tool definitions. Send the selected tool name and JSON arguments to /v1/tools/call, then return the JSON result to the model as that provider's tool result. Do not let the model choose arbitrary GitHub URLs, branches, or repository names; the server pins those to environment configuration.

## Safety and limits

- Project writes are restricted to projects/<slug>/.
- Each project can contain at most 40 files and 500 KB total UTF-8 content.
- JSON files are parsed before any GitHub write.
- Branch names are generated by the server.
- Changes are submitted as pull requests; merging remains a human decision.
- Never execute generated scripts or install generated dependencies as part of validation.
- Add deployment-level rate limiting, request logging without secrets, and abuse monitoring before exposing the API publicly.
